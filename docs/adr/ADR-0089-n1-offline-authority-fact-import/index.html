ADR-0089: N1 offline authority-fact import and node-store verification

Status

accepted (2026-10-27), fixture-only. Proposed 2026-10-24 and revised 2026-10-27 against main (f29d04a2). The maintainer (Matt Faherty, the decider) accepted it on 2026-10-27 under ADR-0018, as an architectural decision limited to the fixture-only offline authority-import experiment, subject to the restrictions and implementation prerequisites in this text. The acceptance covers the architecture and contract only. It does not approve, implement, deploy or operate an importer. Implementation status is separate (ADR-0018 §3): nothing here is implemented.

The maintainer explicitly approved these choices for this initial scope:

  1. Root execution is prohibited. The importer runs as the unprivileged account that owns the data directory (§5). Existing root-run container deployments are unsupported for importing.
  2. Withdrawal during an incomplete import is deferred. Recovery completes the previously validated fixture segment before new retention decisions take effect (§6, §8). This is not a precedent for real participants' consent.
  3. Retention limits are provisional and fail closed. Exhausting a Subject's capacity may block later facts, including revocations (§8). This is acceptable only while results gate no real effect.
  4. The facts-only history-segment format (§3) is accepted as a proposed implementation contract. Its canonical domain, encoding, independent reference vectors and compatibility obligations must be verified before any implementation merges.
  5. No completeness or freshness guarantee is established (§4). Authority evaluation stays relative to the node's retained history.
  6. Not approved: real participants, institutional credentials, production authority, network ingestion, and operational authorization consumers.

The fixture: retention basis remains an operator assertion, not a cryptographic proof (§8). Fixture-provenance enforcement (for example, accepting only Subjects whose inception carries a context nonce from a published fixture set) is an explicit implementation review item for the icnctl slice. No other governance or institutional permission follows from this acceptance; the decisions in §13 and §14 stay open.

Review history. Drafted and revised by an agent. Reviews of the text were by independent review agents; beyond the maintainer's acceptance decision, no human review is claimed. A FULL generation by two reviewers (identity and privacy; security and recovery) found six blockers, all fixed in one batch; a DELTA review found one new blocker in that batch (a sync relying on sled's close, which ADR-0088 §5 rejects), fixed by a targeted correction; targeted reviews of each later amendment (editorial wording, the symlink-safe durability walk) closed with no blockers. Risks accepted knowingly are recorded in §4, §6, §8, §12 and "Irreversible commitments".

Context

main can persist N1 facts durably (ADR-0087), rehydrate them fail closed at every daemon start (ADR-0088), and answer derive over the result. It has no producer: AuthorityRegistry::ingest has no production caller, and every fact on any node was written by a test. It has no consumer either: nothing makes an authorization decision from N1 state.

N4-A answers "did device D hold capability C from Subject S at position E" over an AuthorityStore. N4-B's EvidenceBundle carries the evidence for one device act: the facts derive_prefix reads up to the act's evaluation position E, plus the act. N4-E answers the same question at a relying party's current position.

A bundle is the wrong carrier for history. It cannot exist without an act, and it cannot carry a fact after E. A node fed only bundles would learn a Subject's history only up to positions where some act happened, and would never learn a later revocation unless another act's bundle happened to include it. N4-E current admission over that node's facts would then admit a device its Subject has revoked. This revision therefore introduces a facts-only carrier for history (§3) and keeps the bundle for what it is: evidence for one act (§10).

The smallest producer that adds no network surface is an offline operator tool that imports a history segment into a stopped node's store. This ADR defines what that tool may do and, as importantly, what it may not claim.

Decision

1. Seven properties that must stay separate

Property Meaning Established by Does not imply
Cryptographic validity key K signed these canonical bytes verify_strict inside N1 admission that K had any authority
N1 admission the body is canonical, in bounds, and verifies under its inline signer admissible (ADR-0087 §5) authority; that the history is complete
Durable persistence the record survived the store's durability barrier put_fact Ok (ADR-0087 §4) power-loss durability; that the node may keep it
Retention record the operator recorded a decision to keep this Subject's facts, for a stated context §8: written before import permission, consent, institutional authorization, or anything about the Subject's authority
Completeness and freshness the node holds every fact that exists, up to the Subject's real tip nothing (§4) —
Derived authority what derive concludes from the retained facts derive / derive_prefix over the rehydrated store that the node holds every fact that exists
N4 relying-party enforcement a device act is accepted at a relying-party-chosen position verify_device_act / current admission (N4-A, N4-E) that any effect is gated on it today

The import tool establishes admission and durable persistence for each fact it writes, and checks that a retention record (§8) exists before writing any. It never evaluates, and never reports, completeness, derived authority or enforcement as a property of the import.

2. Scope of the producer

  • One command, icnctl authority import <segment-file>, run by the node operator against a stopped node. It takes the data-directory lock; if icnd holds it, the import is refused.
  • Input is exactly one history segment v1 file (§3). EvidenceBundle is not an import input in this version.
  • No network listener, IPC socket, gateway route, gossip or N3 ingest, and no credentials. A running daemon sees imported facts only at its next start, through the existing rehydration.
  • Fixture Subjects only (§8).

3. The history segment (candidate format, v1)

A history segment is a canonical, facts-only excerpt of one Subject's N1 history over a contiguous position range. It carries no device act and asserts nothing about authority.

Fields. subject: SubjectId, from: u64, to: u64, and facts: a map from EventId to { body: AuthorityBody, witnesses: set of WitnessSignature } (the same BundledFact shape as N4-B).

Canonical encoding (the N1/N4 Writer conventions: big-endian integers, lp = u32 length prefix, b32/b64 fixed arrays):

lp("icn.n1.history-segment")      domain (proposed literal; registered in the
                                  domain-separation audit before any implementation)
u16  version = 1
b32  subject
u64  from
u64  to
u32  fact_count
repeat fact_count, ascending by event_id:
  b32  event_id
  lp   body.canonical_bytes()
  u32  witness_count            (>= 1)
  repeat witness_count, ascending:
    b64  witness signature

segment_id = SHA-256(canonical bytes). Strict decode: the encoder's output is the only accepted form, and trailing bytes are refused.

Validity rules (all checked by decode or by whole-segment admission, before anything is written):

  1. 0 <= from <= to <= MAX_POSITION.
  2. Every fact's body.subject() equals subject, and its event_id equals the hash of its body.
  3. Every fact's position lies in from..=to.
  4. Continuity: every position in from..=to holds at least one fact.
  5. Linkage: every fact at position p > from names in prev_digest a fact this segment holds at p - 1. If from == 0 the segment holds the inception, whose event id is subject.
  6. Facts ascend strictly by event_id; witnesses ascend strictly within a fact; every fact has at least one witness.
  7. Every (body, witness) pair passes N1 admission, and the segment as a whole admits into an empty in-memory store (admit), all or nothing. A bad witness must be refused here, before anything is written, not by ingest part-way through an import (where every resume would refuse it again).

At import (against the node's retained facts), one more rule: if from > 0, every fact at from must name in prev_digest a fact the node already retains for the same Subject at from - 1. A segment that would leave an unanchored fragment is refused. Retaining facts that derive cannot reach would cost retention without any use.

Competing candidates. Several admissible facts at one position are allowed in a segment (rule 4 says "at least one"). They are evidence of a fork and are kept (§9).

Refusals (each a distinct error): framing; version; range out of bounds; fact for another Subject; event id mismatch; fact outside range; gap in continuity; broken linkage; ordering (facts or witnesses); missing witness; inadmissible fact; unanchored at import; any bound in §8.

4. What a segment cannot establish: completeness and freshness

Holding a valid segment proves only that these facts are admissible and form a contiguous, linked excerpt over from..=to. It does not prove:

  • that to is the Subject's tip. Later facts, including revocations, may exist.
  • that no competing candidate exists at any position the segment covers. An omitted fork candidate is undetectable at or below to (the same limit as N4-B §3.3).
  • freshness. There is no clock or authority that dates a segment, and a segment can be replayed from any earlier time.

A node therefore holds a retained tip per Subject, never a "current" one. Every answer computed from a node's store is "as of the facts this node retains" (§10, §12). Nothing here changes how a relying party must treat incompleteness; any future consumer must address it in its own ADR.

5. Opening the store offline

AuthorityRegistry::open is the daemon's start: it may initialize a fresh history, and it always writes the startup receipt. An offline tool must do neither. A separate entry point is specified, AuthorityRegistry::open_offline(data_dir, lock, access) with access one of Inspect, Import or Resume:

  • Ownership and permissions are checked first, before the lock is taken and before the N2-A gate runs, because both create files: the lock acquisition can create the lock file, and the gate opens every sled store and writes its own receipt. The tool refuses unless the effective uid is not 0 and owns the data directory, store/, store/authority and the existing lock file; neither the data directory nor store/ is group- or other-writable; and store/authority grants no group or other permissions (ADR-0088 §11 already keeps it 0700). The data directory may otherwise follow the umask, as ADR-0088 §11 allows. sled has no read-only open and creates files as it runs; an offline tool run by another account, or by root, would leave files the daemon's account may not be able to open, wedging the node.
  • It then takes the storage lock without creating it (the data directory must already have been initialized by icnd), runs the N2-A gate (ADR-0088 §7's order), and refuses an incomplete restore, like open. open_offline repeats the ownership and permission checks immediately before sled opens the store, to narrow the window between check and use.
  • It opens only an initialized store whose record and instance row agree. Every other ADR-0088 §6 state (no record, missing store, replaced store, interrupted initialization) is refused. A new authority history is created by icnd only.
  • It writes no startup receipt. Import and Resume remove the previous receipt with the existing AuthorityRegistry::discard_receipt before writing any fact, because once facts change that receipt misdescribes the store. Inspect leaves it alone.
  • Inspect and Import refuse while an import is incomplete (§6). Resume requires it.
  • "Writes no facts" is not "writes nothing": the N2-A gate writes its receipt, and sled may write its own files, on every offline open, including Inspect.

6. Atomicity, interruption and resumption

Per-fact durability stays as ADR-0087 defines it. A segment is not made atomic in the store, and nothing may describe an import as atomic. Whole-segment admission in memory proves the segment is well formed; it does not make the writes atomic.

Why a partial import must not be used silently. A partial import is not wrong authority in itself: a gap stops the derive frontier. What it breaks is the operator's knowledge of what the node holds. If an import stops after a device's authorize is durable but before the later revoke is, the retained tip is behind the facts the node was handed, and N4-E at that tip still admits the device. Durable partial state is therefore permitted on disk but must be fail-closed and resumable:

  1. Decode the whole segment strictly, apply §3 and §8, and admit it in memory. Anything refused writes nothing.
  2. Write the segment bytes to the staged file (a regular, owner-only file in the data directory), fsync it, and fsync the directory, so the staged file's directory entry is durable too. Only then write the import-incomplete marker (synced temporary file, then a rename that refuses to replace an existing entry, such as RENAME_NOREPLACE, after checking under the lock that no marker exists), and fsync the directory. The marker records the segment id, Subject, fact count, and a snapshot of the retention entry and bounds in force when the import began. On storage that honours fsync, a durable marker therefore always has a durable staged copy behind it; on storage that does not, nothing here holds, as for the restore marker.
  3. Remove the startup receipt (§5).
  4. Write each fact through ingest (admission, durability barrier, publication), in ascending position order, then ascending event_id.
  5. After the last barrier, make the store fully durable before touching the marker: the per-fact barrier is sled's flush, which is process-crash safe but only best effort against power loss (ADR-0087 §4, §9). Closing the store is not that step: ADR-0088 §5 already rejects closing sled to force a sync (its close is a Drop that returns nothing, skips I/O after an earlier error, panics on a failed fsync, and runs only when the last handle drops). Instead, after every handle to the authority store has been dropped, the tool runs the durability walk below over store/authority and proceeds only if it succeeds. Any failure, including a panic in sled's own drop, leaves the marker in place (an implementation must not catch that panic and continue to the sync step), so the node stays fail closed and --resume repeats the walk. Only then remove the marker and fsync the data directory. Otherwise a power loss could keep the marker's removal while losing trailing facts, such as a revoke, and the daemon would start on exactly the partial state the marker exists to expose. Only after the marker is gone remove the staged copy. A stop between the two leaves an orphan staged copy and no marker, which is harmless and is removed by the next import.

Existence is the safety property, as for the restore marker: any entry at the marker's name refuses, and so does any error other than "not found" while looking. It is removed only by a completed import or resume. Nothing removes it on drop.

Recovery is icnctl authority import --resume. It re-reads the staged copy (or the original file if the operator supplies it), checks its id against the marker, re-applies §3, and writes the facts again. Duplicate writes are semantically idempotent (ADR-0087 §3), so resuming after any interruption point is safe.

Resume evaluates retention and bounds against the snapshot in the marker, not the current retention file, after re-validating the snapshot itself: its basis must still begin fixture:, its bounds are clamped to the compiled maxima (configuration may lower, never raise), and no allocation is sized from the marker's recorded fact count. A hand-written marker therefore cannot raise a bound or admit a non-fixture basis. Resume also counts bounds over the union of distinct records (retained ∪ segment), so the facts the interrupted import already wrote are not counted twice. A withdrawal or a lowered bound made while an import is incomplete therefore cannot wedge the node: it takes effect for later imports, and the completing import's report states that retention changed after the import began. Completing the import writes the rest of a segment the operator had already decided to retain; it does not create a new retention decision. Retention edits are meant to be made when no import is incomplete, and tooling that edits the retention file should refuse while a marker exists.

There is no "abandon" in this version. Facts already written cannot be removed (the store has no erasure path), so abandoning would leave exactly the stale partial history the marker exists to expose. Whether a governed abandon or erasure exists is a governance decision (§14).

Never wedged (an acceptance obligation, not a hope), for interruptions of the import process (crash, kill, or power loss on storage that honours fsync), with the staged copy or the original file available. If both the staged copy and the original file are lost or corrupt, or the marker itself is unreadable, resume cannot proceed and the node stays refused; the documented operator procedures are to obtain the same segment again (matching segment_id) or to restore the data directory from a backup taken before the import (ADR-0088 §12). An implementation is acceptable only with a fault-injection suite that stops the import after staging, after the marker, after k of n facts (k = 0, 1, n-1, n), between the last barrier and the store fsyncs, during them (including a failed fsync), between them and the marker's removal, and between the marker's removal and the staged copy's removal. In every case the daemon must refuse while the marker exists, --resume must complete, the final store must equal a clean import's, and no case may leave the node permanently refused. The suite also covers a withdrawal and a lowered bound made while the marker exists, and a resume near the per-Subject bound. A store damaged in a way the durability walk refuses (a planted symlink, an unexpected file type) is outside this obligation: the node stays refused until the operator repairs the store, and the refusal names the entry.

The durability walk. O_NOFOLLOW guards only the last component of a path, so the walk never opens a path that contains a directory it has not itself opened:

  • It starts from a descriptor for the data directory whose fstat identity (device and inode) matches the directory §5 checked and the lock anchors. From it, it opens store, then from that descriptor authority, one component at a time, each with O_NOFOLLOW | O_DIRECTORY, and checks with fstat that each is a directory owned by the effective uid (§5). A symlinked store or authority is therefore refused, never followed.
  • It descends only through descriptors: each entry is opened with openat relative to its parent directory's descriptor, with O_NOFOLLOW | O_NOCTTY, plus O_DIRECTORY for directories and O_NONBLOCK for regular files. Every opened descriptor is checked with fstat against the entry's type before it is used. No multi-component path is ever opened. The walk refuses below a depth of 8 directories under store/authority (sled's layout is about two levels deep; the N2-A gate's discovery uses a similar bound) and closes each descriptor after its fsync.
  • It classifies each entry by the type readdir reports; where that is DT_UNKNOWN (some filesystems report it for every entry), by fstatat(parent, name, AT_SYMLINK_NOFOLLOW). It refuses any entry so classified as a symlink, FIFO, socket, block or character device, or any type other than a regular file or a directory, without opening it. If an entry is swapped between readdir and openat, the open flags still fail closed (ELOOP for a symlink, O_DIRECTORY for a wrong directory type, O_NONBLOCK so a FIFO cannot block) and fstat refuses the result; a device node swapped in at that instant can be opened before fstat refuses it, and O_NOCTTY keeps that open from acquiring a terminal. Only the owning account or root can make such a swap (§5).
  • It fsyncs every regular file and every directory it opened, including store/authority itself and every subdirectory such as blobs/, and succeeds only if every openat, fstat and fsync succeeded.
  • On any refusal or failure the marker stays in place and nothing further is removed.

A refusal for a planted symlink or an unexpected file type is expected fail-closed behaviour, not a "never wedged" violation: only the account that owns the store (or root) can plant one there (§5). Resume repeats the walk and refuses again until the operator repairs the store, for example by removing the planted entry, so --resume can complete. The same rule already applies to the N2-A gate's discovery of sled roots, which refuses any symlink.

7. Reconciliation with daemon startup: what changes

icnd starts in this order (main.rs): take the data-directory lock, discard_receipt, run the N2-A gate, AuthorityRegistry::open. The marker fits that order without moving any step:

Component Change
icn-core import_marker (new) Create, read and complete the marker and staged file. Modelled on restore_marker (existence refuses; fsync of file and directory; no removal on drop), but created by temp file plus a no-replace rename after an absence check under the lock, so it is never torn and never silently replaces an existing marker.
icn-core AuthorityRegistry::open After refuse_incomplete_restore, refuse ImportIncomplete while the marker exists. The daemon's start then fails closed, naming icnctl authority import --resume.
icn-core AuthorityRegistry::open_offline (new) §5.
icn-core RegistryError New ImportIncomplete { marker, subject, segment_id }.
icn-core DataDirLock Unchanged. Unlike the restore marker, the import marker is not checked at lock acquisition: resume must take the lock, and the condition only makes the authority store untrustworthy, not the rest of the data directory.
icn-core discard_receipt Unchanged. An import has already removed the receipt before its first write.
icn-store N2-A gate Unchanged. The marker and staged file are top-level regular files, never directories, so they are not discovered as sled roots. A test must show this.
icnd main.rs No ordering change. The startup error surfaces the new refusal and its recovery command.
icnctl New authority import [--resume] and device-authority verify --node-store (§10). Backup and restore carry the marker and staged file with the data directory, so a node restored from a mid-import backup refuses until resumed (intended). Reporting the marker in verify-backup is a follow-up.
ADR-0088 Amended (see "Effect on ADR-0088"): §6 gains the import-incomplete state; §11's exposure statement extends to imported facts once an importer exists; §12 gains import recovery.

8. Retention: fixture Subjects only, with explicit context and scope

Admission accepts any self-incepted Subject, and the store only grows. Without a retention rule, any segment the operator is handed becomes a permanent record on the node, and a node collecting Subjects across contexts works against IDENTITY_SEMANTICS §5.1 (one SubjectId per institutional context) and §5.3 (the identifier is public to its context only).

  • Retention file. An owner-only (0600) file in the data directory lists each Subject the node may keep. Each entry records the subject, the context it is retained for, the basis (a reference, never personal data), who added it, and when. A segment whose Subject has no entry is refused before anything is written.
  • Fixture only (v1). An entry's basis must begin fixture:. Any other basis is refused. The prefix is the operator's declaration, not a technical control: anyone can type it in front of a real Subject. What keeps real participants out is §13, which needs people, and the operator's obligation not to mislabel. An implementation may add a content check, for example accepting only Subjects whose inception carries a context nonce from a published fixture set (the N4 test vectors), since a compliant real Subject cannot carry a fixture nonce. N4-A §9.3 already forbids promoting fixture identities into anything real. No real participant may be retained until §13 is met and a later revision of this ADR permits it.
  • Context is recorded per Subject, never assumed per node. A node may host several autonomous institutional domains, and a person may hold context-specific Subjects in overlapping communities, cooperatives, federations and other institutions. Until GEN (#2602) binds a Subject to a context structurally, context is the operator's recorded claim, not a verified fact. It is never used to join or compare Subjects. The label is not the only correlation path: authorize, revoke and establishment facts carry Principal keys, which are correlatable across contexts by construction. A node retaining Subjects from several contexts can link any of them that reuse a device key, and the startup receipt already lists every retained Subject's keys in one file. Separation therefore also depends on clients using one device Principal per (device, context) (N4-A §9.3), which a node cannot verify. A first implementation may support one context per store as an implementation limit; that limit must not become an ICN substrate invariant.
  • The retention file is the operator's record of a retention decision. It is not the person's consent or the institution's authorization, and nothing may treat an entry as either.
  • Provisional bounds, checked before reading or allocating: segment file at most 1 MiB; at most 4,096 facts per import; at most 16 witnesses per fact; at most 65,536 retained facts and 262,144 retained (fact, witness) records per Subject, counted over distinct records. Witness records are bounded separately because a key holder can mint distinct valid signatures over the same body. Configuration may lower these, never raise them. Values to be confirmed by testing. A Subject that reaches a bound refuses every later import, including one that carries a revoke; since admission is state-independent, anyone holding a valid key for the Subject can fill its bounds. The refusal is open, not silent, but a node in that state can no longer learn of revocations for that Subject, and N4-E over its facts stays at the stale tip.
  • Withdrawal. Removing an entry stops further imports for that Subject. It does not remove retained facts: the fact store has no deletion API, sled can keep deleted bytes, an account that held an open descriptor keeps it (ADR-0088 §11), and backups keep their own copies. A withdrawn Subject's facts are still rehydrated at every daemon start and listed, with their keys, in the startup receipt; still answered by --node-store; and still named in the retained import reports. Imported facts carry no record of which import wrote them, so a later erasure could not attribute facts to imports from the store alone. A withdrawal made while an import is incomplete is deferred: the import completes and writes the rest of that segment for the withdrawn Subject (up to the per-import bound) before the withdrawal takes effect (§6). That is forced by the absence of an abandon path, and harmless for fixtures; for real participants it is a consent-semantics choice, and whether a withdrawal may instead override completion, accepting a stale partial history, is a governance decision (§14).
  • No new index. Reports and the retention file name SubjectIds only. Nothing maps a legacy Did or any other identifier to a Subject.

9. Forks are evidence

An import never filters facts by what derive would conclude. If the retained facts, or the union of retained and imported facts, contain admissible competing candidates at one position, all are kept, and derive reports the Subject as halted. The import report states the halt. Dropping a candidate would hide the duplicity that halting exists to expose. A segment that leads to a halted Subject is not an import failure. One exclusion is structural, not a filter: §3's linkage rule keeps admissible bodies whose predecessor is not in the segment (or, at from, not retained) out of a segment. derive could not select them, so no duplicity is hidden, but an N4-B bundle may carry such bodies and a segment may not.

10. icnctl device-authority verify --node-store

An offline check of a device act, given as an N4-B EvidenceBundle, against the node's own retained facts. It uses open_offline(Inspect) under the same lock, refuses while an import is incomplete, writes no facts, and neither writes nor removes the startup receipt (the N2-A gate still writes its receipt, and sled may write its own files, §5). It reports, separately: the historical verdict (N4-A, at the position the act binds), and the N4-E current-admission verdict over the node's retained facts, in N4-E's own vocabulary. N4-E evaluates at the retained frontier minus one and requires the act to bind exactly that position, so for an act bound to an earlier position the verdict is a refusal such as StaleAct, and a halted Subject gives AuthorityHalted. It names the retained tip and labels every answer "as of the facts this node retains"; it never calls the retained tip current. The bundle's own facts are not imported.

11. Import reports

An import writes an owner-only import report, a different file name and format from the startup receipt and never called one: segment id, Subject, from..=to, facts and witnesses written, facts already present, the retained tip, and a summary of the derive view afterwards (its state, such as active or halted, and counts of authority keys and devices; never the keys themselves), labelled as a diagnostic in the way ADR-0088 §10 labels the receipt. The last 8 reports are kept; older ones are removed by the next import. Reports and logs carry digests, counts and SubjectIds only, never fact bodies, keys or payloads.

12. How the limits are communicated

Every import report and every --node-store answer states, in fixed text:

  • Imported facts are admitted, not authorized. Authority is what derive concludes, at the point of use, over the facts held there.
  • A segment cannot prove it is complete or current (§4). The node holds only what it was given. There is no replication (N3).
  • Rolling the data directory back, or losing it entirely, cannot be detected (ADR-0088 §9).
  • Persistence survives a process crash. Surviving power loss is best effort per fact (ADR-0087 §4, §9); an import fsyncs every file of the authority store with its own descriptors, and checks each result, before clearing its marker (§6), on storage that honours fsync.
  • If the store was ever readable by another account, anything imported later is exposed to an open descriptor that account may still hold (ADR-0088 §11).

13. Prerequisites that need people, not code

Before any fact about a real participant is retained:

  1. A later revision of this ADR, accepted by the maintainer, lifting §8's fixture-only rule (this ADR's acceptance of 2026-10-27 covers fixture Subjects only).
  2. The decision of the institution, or other context authority (IDENTITY_SEMANTICS §2.2 allows non-institutional contexts), on whose facts a node may keep, in which context, on what basis, with what notice that retained facts cannot currently be erased, and who may run the import.
  3. A withdrawal and erasure procedure, or an explicit institutional decision to proceed without one.
  4. A custody decision for the real Subject and device keys that sign the facts. Facts are authored only by the Subject's keys; assembling or carrying a segment (by the Subject's client, or later by N3 relaying) is carriage, not authorship. The node never authors facts, and hosting a store confers no authority.
  5. A security review of the import implementation before it runs against a real store.

14. Decisions still open

  • Whether a governed abandon or erasure procedure exists, and who may invoke it (governance).
  • Whether the retention file stays an operator-edited file or becomes a governed record (maintainer, then governance).
  • Who may run an import for a real institution, and how consent is recorded and withdrawn (governance).
  • Final values of the §8 bounds after testing (maintainer).
  • How a Subject's own client produces segments: out of scope here, and needs its own design.
  • For real participants: whether a withdrawal made during an incomplete import may override completion, accepting a stale partial history, instead of being deferred (governance). For the fixture scope it is deferred (Status, choice 2).
  • For real participants: what a node does when a Subject reaches a bound and a later segment carries a revocation (maintainer, then governance). For the fixture scope the bound fails closed (Status, choice 3).

Decided at acceptance for the fixture scope: root execution is prohibited, and root-run container deployments cannot import (Status, choice 1). Changing that needs a later revision.

Irreversible commitments

  1. The segment's domain literal and layout become permanent once published; canonical vectors and an independent reference implementation must exist before any implementation merges.
  2. A new fail-closed state in every registry open; operators handle it for the life of the node. §6's fault-injection obligation is what makes it acceptable.
  3. Retained facts cannot be erased. The fixture-only rule exists because of this.
  4. The retention file's semantics. They must never be read as consent or authority, by this or any later code.
  5. The on-disk names and formats of the marker, staged file, import report and retention file: backup, restore and verify-backup handle data-directory entries by name.
  6. segment_id as an identity (SHA-256 over the canonical bytes).
  7. Imported facts carry no import provenance and reports rotate after 8, so a later withdrawal or erasure procedure cannot tell which import wrote which fact. A provenance record would have to be designed before real participants are retained.

Effect on ADR-0088

ADR-0088 is amended by this ADR (its status becomes amended, with an amendment note; ADR-0018 §4). The amendment is a future contract, not current behaviour: no importer exists, and icnd does not check any import marker today.

  • §6 gains one fail-closed state, import incomplete, which open will refuse once the import marker is implemented (§6, §7 here).
  • §11's "Today no runtime producer writes facts, so nothing is written after the tightening" remains true until an importer exists. Once one does, imported facts are written after the tightening, and the exposure statement covers them (an account that ever held an open descriptor keeps reading).
  • §12 (manual recovery) gains the import-incomplete state and its procedures (§6 here) when they are implemented.
  • §10 is unchanged in substance: the startup receipt stays a daemon diagnostic. Offline tools that write facts remove it and never write one.

ADR-0087 is unchanged.

Security and privacy controls (required of an implementation)

  • Data-directory lock held for the whole import; refused while icnd runs.
  • N2-A gate before open; incomplete-restore and incomplete-import refusals before any write.
  • Ownership and permissions (§5) checked before the lock is taken and before the N2-A gate, and again immediately before sled opens the store; never run as root.
  • The input is opened once with O_NOFOLLOW | O_NONBLOCK; the open descriptor must be a regular file (fstat); it is read with a hard limit of the size bound plus one byte. Every count in the encoding is checked against the bytes remaining before anything is allocated, and decoding is strict. The retention file and the marker record are parsed with their own size bounds (64 KiB each).
  • Whole-segment admission in memory before the marker. Per-fact admission, then barrier, then publication.
  • Marker, staged copy, import report and retention file are each created owner-only (0600) as top-level regular files in the data directory.
  • Logs carry digests, counts and the SubjectId only. Never fact bodies, keys or payloads.
  • No network, IPC or credential dependency. No real identity material in tests.
  • Acceptance tests for the durability walk: store itself replaced by a symlink; authority replaced by a symlink; a data-directory descriptor whose identity does not match the directory §5 checked; a symlinked intermediate directory under store/authority (for example blobs/ replaced by a symlink to a directory outside the store); a symlinked file; a FIFO, a socket and (where the test can create one) a device node at a file position; and an injected fsync failure on a file and on a directory. In each case the import or resume refuses, names the entry, opens nothing outside the store, never blocks, and leaves the marker in place; after the operator repairs the store, --resume completes.
  • Mutation tests that remove the marker write, skip whole-segment admission, publish before the barrier, filter by verdict, write a startup receipt from the offline path, let open ignore the marker, remove the marker after a failed or skipped store fsync, accept a non-fixture: basis, skip the ownership check, check the size after reading, resume without comparing the segment id, open a child by full path instead of relative to its parent's descriptor, open store/authority as one multi-component path, drop O_NOFOLLOW, follow a symlinked directory, open a FIFO or other non-regular, non-directory entry, or skip the fsync of a directory, must each be caught.

Consequences

  • A node can hold N1 history for fixture Subjects without any new network surface, and the daemon's existing fail-closed rehydration covers it.
  • Revocations reach a node through the same carrier as everything else, so a node's retained tip can include them; it still cannot prove it holds the latest.
  • An operator handles a new refusal (import incomplete), with a resume path instead of a manual procedure.
  • Retention becomes an explicit, recorded decision instead of a side effect of admission.
  • Nothing here creates a consumer. N4 enforcement over a node's store stays a separate decision.

Alternatives considered

Alternative Why not now
Import EvidenceBundles Act-centred and prefix-bounded: cannot carry a revocation after the act's position, cannot exist without an act. Kept for act verification only (§10).
Atomic batch in the store Changes ADR-0087's accepted contract. Possible later by amendment.
Check the marker at DataDirLock acquisition Would block resume and the rest of the data directory for a condition local to the authority store.
Import through a running daemon (IPC, socket, gateway) A new authority write surface. Needs its own design and security review.
Reuse AuthorityRegistry::open Would initialize histories outside icnd and write a false startup receipt.
Filter out facts that make a Subject halted Hides duplicity. Halting is the intended outcome.
No retention rule, admit anything Unbounded permanent storage, and a cross-context correlation surface.
Accept unanchored segments (from > 0 with no retained predecessor) Retention cost with no use: derive cannot reach the facts.
